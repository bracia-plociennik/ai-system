# Response Contract

## Purpose

This file defines the required user-facing response shape for AI System work.

It is communication policy. It does not grant write permission and does not bypass blockers, privacy, validation, or `owner-approved` gates.

For every new planning, implementation, or QA scope, include:

```text
Model recommendation:
- Recommended: <available model and effort, or capability class>
- Reason:
- Criticality:
- Current model known: <yes|no>
- Blocking: no
```

Follow `.systems/ai/core/model-selection-guidance.md`. For unrelated substantive responses, the block may be omitted.

## When It Applies

Use `Co dalej?` for a response that needs an owner decision or handoff. For a small, complete, low-risk answer or narrow edit, finish with the result and verification instead of a ritual next-step prompt.

Responses that require the full next-step footer include:

- decision-ready plans, audit, validation, review, and blocker reports;
- guide, recovery, task-intake, dump triage, memory, distillation, and change-request handoffs;
- substantive implementation closure when a follow-up decision remains.

Do not attach the full footer to every completed typo fix, factual lookup, or self-contained implementation report. This changes presentation only: required post-write operational summaries, approval requests, contract compliance, evidence, and stop conditions still apply when their route requires them.

Do not place the footer inside strict machine-readable output when the owner explicitly requested JSON-only, patch-only, or exact-template output. Put it in the nearest surrounding human-facing response.

## Post-Write Operational Summaries

After a successful owner-approved create or update of a canonical daily check-in or weekly plan, the user-facing response must use this order:

1. `Zapisano:` with the exact paths of the artifacts that were actually written.
2. The route-specific read-only plan summary: `Post-Write Daily Summary` or `Post-Write Weekly Summary`.
3. The actual targeted validation result.
4. The applicable Execution Trace and contract-compliance blocks, then `Co dalej?` when an owner decision or handoff remains.

Re-read the saved canonical artifact before producing the summary. Do not build it from conversation memory, a proposed plan, or an earlier draft. Omit unknown values instead of guessing.

A post-write summary is chat-only. It does not create another file, execute tasks, authorize deploys, send external communication, or grant permission for any external action. When a displayed plan item mentions a deploy, message, publication, payment, or other external action, label it as a recorded plan rather than completed or authorized work.

For a daily check-in write or update in a unified workspace or for native V4, run `.systems/scripts/sync-personal-ops-check-ins-v4 --post-write` before calculating the summary. Only unmigrated V3 uses `.systems/scripts/sync-personal-ops-check-ins-v3 --post-write`; V3 writes are retired after aggregate activation. `--status-only` is not a substitute. The summary may include owner-local budget, calorie, and six-block `food_blocks` projections only when the refreshed official indexes and private workspace configuration are valid. Show IF first as a standalone window line with no calorie or spending sublist. Show the food-block schedule in a separate macro schedule section, selected by planned training/rest mode; the exact `planned_calories_representative` value supplies the independent calorie target. When `food_schedule.status: available`, the response MUST render exactly six macro rows, once each and in this order: `09:00-11:00`, `11:00-13:00`, `13:00-15:00`, `15:00-17:00`, `17:00-19:00`, `19:00-21:00`. Every row must show one of the statuses `configured|empty`; configured rows must show kcal, protein, fat, and carbohydrates, while empty rows must show no numeric intake values. A daily macro total is supplementary and never replaces these six rows. The summary is incomplete if any row is omitted or reordered. Show the daily budget in a separate budget section. Then show training and NSDR. If planned training/rest data are missing or ambiguous, do not guess the profile and mark the schedule unknown. A partial food-block configuration is `food_schedule.status: unavailable` with a deterministic reason; it does not mean the entire budget projection failed. If the refresh fails, keep the canonical write durable, report `index refresh: failed`, and do not claim current indexes or full validation success.

The daily plan block must be generated by the deterministic canonical renderer, not reconstructed manually from conversation context. Native V4 uses `.systems/scripts/render-personal-ops-daily-summary-v4`; the legacy V3 route uses the following command:

```text
.systems/scripts/render-personal-ops-daily-summary --workspace <workspace> --date YYYY-MM-DD
```

After a successful post-write refresh, re-read the saved artifact and paste the renderer output verbatim. The selected version's renderer with `--check-file <path>` is the evaluator for a captured block; it tolerates only a final newline and rejects missing or reordered macro rows, changed source values, or execution claims. The renderer is read-only and does not execute tasks or external actions.

If the write fails, do not say `Zapisano:`. If targeted validation fails, say `Walidacja targeted nie przeszła` and list the failed check; never report that validation passed.

### Post-Write Block Checkpoint Summary

After a successful `block-boundary` checkpoint write, re-read the new checkpoint and its `latest.md` router before responding. Return a chat-only summary containing the exact written paths, block identity, last completed step, next step, blocker, scope fate, delivered and unfinished scope, resume instruction, evidence paths, and the actual targeted `check-block-checkpoint` result. This summary does not execute the next step or grant permission for memory, distillation, TaskNotes, project changes, commits, pushes, or external effects.

### Post-Write Daily Summary

Use the daily route rules in `.systems/ai/core/personal-ops.md`. The summary must exclude prior-day closure, Raw Check-In, OCR, and attachment content.

### Post-Write Weekly Summary

Use the weekly route rules in `.systems/ai/core/weekly-planning.md`. The summary must expose unavailable days, capacity limits, deferred scope, and TaskNote generation status when present.

## Work Closure Gate

When a substantive response closes a unit of work, performs a handoff, reports an accepted change, or prepares commit-ready or push-ready product-development work, apply `.systems/ai/core/contract-compliance.md` before the `Co dalej?` footer.

Use this block:

```text
Contract compliance:
- Work mode: <project|micro-task|micro-project|side-task|system-maintenance|client-work>
- Work mode compliance: <pass|warning|blocked>
- Knowledge capture: <required|not-required>
- Capture target: <status/evidence|workspace-memory|primary-entity-memory|client-memory|owned-asset-memory|project-memory|distillation|checkpoint|external-memory|system-insights|not-applicable>
- Reason: <short reason>
```

This gate is advisory-only. It records the Knowledge capture decision before `AI_SYSTEM_WORK_CLOSURE`; it does not grant write permission or bypass privacy, evidence, validation, stop conditions, or owner approvals.

If End-of-Task Capture is used, apply `.systems/ai/core/end-of-task-capture.md` and include the required `End-of-Task Capture` block before the `Contract compliance` block when both apply. The trace must state whether End-of-Task Capture was the matched route or supporting output, source scope reviewed, durable writes performed or skipped, and residual risk.

For substantive system-maintenance upgrades before commit or handoff, include:

```text
Cross-system impact:
- Owner decision: <yes|no|pending>
- Counterpart: <ai-workflow|ai-system|none>
- Handoff artifact: <path|not-required|pending>
- Reason:
```

Use `.systems/ai/core/cross-system-upgrade-handoff.md`. `pending` blocks commit and handoff.

Quality closures use the Validation Execution Record from `.systems/ai/core/validation-routing.md`. Scripts remain supporting-only.

## Delivery And Distillation Trace

When Delivery Constraints apply, report the agreed deadline/timebox, delivered and deferred scope, overrun status, cutline use, and whether the quality floor was preserved.

When a Distillation State record applies, report its state, derived `is_distilled` value, source/quality evidence, owner disposition, and next consumer. These fields are evidence only and do not grant writes, promotion, commit, push, or work closure.

For an eligible micro-change without a state record, report `Distillation State: micro-exempt` and the reason; do not manufacture `is_distilled` or skip focused QA.

## Decision And Handoff Footer

When `Co dalej?` is required, use this shape:

````text
Co dalej?

Rekomendacja:
<one concrete next step>.
Wpływ: <what this unlocks, protects, or makes clearer>.
Napisz:
```
<copy-paste prompt for the recommended path>
```

Alternatywa:
<one safe alternative next step>.
Wpływ: <tradeoff and when this path is useful>.
Napisz:
```
<copy-paste prompt for the alternative path>
```
````

For V4 artifacts, paste the output of the canonical renderer verbatim. Do not reconstruct the chronological table or weekly scorecard from chat memory. Preserve unknown values and omit Raw Check-In, OCR, attachments, and historical private detail from the read-only projection.

`Working Dump` is also excluded from Daily Summary. The Weekly Summary may include the renderer's read-only `Kandydaci z Working Dump` section sourced from non-empty Monday-Friday Daily V4 dumps; it must show source dates and proposed types without quoting sensitive literals or claiming any durable capture. No dump content may authorize execution or create a TaskNote without separate owner approval.

The V4 daily renderer must emit `Plan na dziś - <Polish date>, <Polish weekday>` followed by the chronological `Czas | Element | DoD | DL` table. Table entries use separate inline markers for their explicit stream: `Build`, `Deliver`, `Promote`, `Self`, or `Close ones`. The linked WIG item retains its stream marker and adds a separate `WIG` marker; for example, `WIG` plus `Build`. Missing stream/category metadata is not inferred beyond the system-owned schedule block semantics.

Immediately after the table and unallocated items, render `Stan i kierunek dnia` from private canonical `current_state_json`, never from review data or Raw Check-In. It includes mental and body scores with source notes and deterministic operational guidance, constraints with explicit mitigations, work and organism modes with source reasons, and the planned `Self` and `Close ones` outcomes. Historical V4 artifacts without this optional object show `nie podano`; the renderer must not backfill current state from the prior-day review.

The table includes configured meals with their projected kcal and macros. When a configured food block has no explicit meal row, the renderer uses the free interval at the beginning of that block and clips it at the next scheduled event. If no free interval exists, it preserves the configured food interval and exposes a schedule conflict instead of hiding nutrition data.

Below the table, V4 must retain the WIG/DoD/DL, standalone IF window, exactly six macro rows and totals, TaskNote status, warnings, and the complete private budget projections returned by `calculate-personal-ops-budgets`. Spending includes the daily limit, monthly base, buffer, current spending, remaining base, remaining days inclusive, average per remaining day, pace overrun, no-spend days from today, and standard-spend resume date. Calories include the weekly limit, actual intake before today, remaining before today, today's plan, remaining after today, remaining days after today, mechanical limit, common-sense limit, and unbalanced balance. Training and NSDR remain outside the budget sections.

## Recommendation Sources

Choose the recommendation from the highest applicable source:

1. The owner's explicit intent when safe.
2. Task intake result from `.systems/ai/core/task-intake.md`.
3. Current workspace, client, project, dump, memory, checkpoint, or decision status.
4. Stop conditions from `AGENTS.md`, privacy, dump triage, and context-as-data policy.
5. Guide and command routing.
6. Missing runtime defaults: if status or routers are missing, recommend creating or repairing them before doing work.

If sources conflict, recommend recovery or reconciliation instead of guessing.

## Alternative Rules

The alternative must be safe and meaningfully different from the recommendation.

Good alternatives include:

- read-only audit before writing;
- manual owner review before movement;
- narrower dump classification;
- memory distillation before system-insights promotion;
- status reconciliation before implementation.

The alternative must not skip approval, evidence, validation, privacy checks, or stop conditions.

Both `Napisz:` prompts must be directly usable.

## Blocked Work

If blocked, the recommendation should resolve the highest-impact blocker.

The response must state:

- what blocks progress;
- what evidence or decision is missing;
- the exact owner action needed.

Do not suggest implementation as either option while a required blocker remains.
