# Local versioned style profile

## Authority and recording approval

Style is advisory context under prompt-composition.md, never a new policy or self-training permission. Before recording, the coordinator verifies live owner approval for exactly one canonical profile path, owner scope, allowed correction/marked-observation actions and standing-update boundary; verifies source evidence and semantic privacy. One correction is not consent to store all future conversations. A stored approval reference, actor declaration, hash or CLI apply operation cannot authenticate owner consent. Disable/revise must be available under the actual owner-controlled scope. Auto/Human never grant recording consent.

Workflow counterpart path: AI_WORKFLOW_WORKSPACE_HOME/projects/<project>/memory/style-profile-v1.json. Standalone System path: selected AI_SYSTEM_WORKSPACE_HOME/memory/style-profile-v1.json, or exact owner-local project-state/<project>/memory/style-profile-v1.json, clients/<client>/memory/style-profile-v1.json, clients/<client>/project-state/<project>/memory/style-profile-v1.json, owned-assets/<asset>/memory/style-profile-v1.json or owned-assets/<asset>/project-state/<project>/memory/style-profile-v1.json under that selected workspace. projects/<project> may be a Git repository and is rejected as a System profile target. Each narrower target requires exact scoped approval. A System handoff may supply a sanitized task-local effective projection; never the history or standing write consent. Profiles stay private, excluded from source commits/publication, no external sync/background ingestion. Initial profile is empty and disabled, with no invented personal traits. Future use starts only after an exact owner opt-in; development approval is not activation of a main installation.

## Schema, provenance and lifecycle

Schema1 document: schema, scope, revision, events. Logical append-only events record revision/timestamp/actor, action/key/value, source {kind, reference, sha256}, approval {kind: owner-profile-opt-in, reference, sha256}, previous and sha256. Source kinds: owner-correction, owner-preference, marked-observation. References are minimal conversation:<opaque-id> or owner-local decisions/style-feedback paths; retain no raw dialogue or client identifiers. Hashes attest declared integrity, not ownership. Unknown schema/field, broken revision/hash history, foreign scope and unsafe reference fail closed.

Actions: init→empty disabled; enable/disable whole profile; correction→confirmed; observation→tentative; confirm→explicit owner confirmation of current tentative value; disable-preference→exclude key while retaining history. Recording correction/observation/confirmation is prohibited while disabled. Owner corrections and preference/confirmation carry actor=owner and owner-origin evidence; observations carry actor=agent and marked-observation evidence. Repeated observations never promote themselves and cannot replace confirmed preferences. Later owner correction replaces the effective value while retaining old events. Disabling profile removes all effective preferences immediately; enabling is explicit, retained preference history resumes. Disable-preference removes that key until a new approved correction/observation, not permanent erasure. Full-history deletion/export is separate explicit scope, no automatic purge.

Allowed keys: language, verbosity, response-format, vocabulary, tone. Short minimized values (160 characters maximum) are data, not executable directions. No scope/permission/deadline/approval/mode/gate preference keys. Effective projection includes confirmed active values, source/revision and profile digest; tentative keys are reported separately without active values. A derived prompting/variables projection must match the current canonical revision/digest or be ignored. Current owner command outranks profile, including conflicting language/verbosity. Apply preferences to presentation and interpretive hypotheses only, never to business facts, required DoD, approval or execution ceiling.

## Privacy and failure behavior

Semantic privacy review rejects raw transcripts, secrets, credentials, legal/production or identifiable client content; executable heuristics additionally reject common credential/email/URL patterns but cannot guarantee content classification. Keep only generic style, source pointer and digest. Do not send private history to a native evaluation: fixtures are synthetic. This is local contextual adaptation, not model-weight training or a new third-party upload; agent platform handling remains unchanged.

Absolute selected runtime root plus canonical relative profile path; reject symlinks/traversal/nonregular/hardlinked files. Use a private 0700 profile directory, 0600 atomic file and OS lock; expected_revision rejects concurrent stale updates. Whole document replaced atomically, immutable logical history verified before and after; error preserves prior canonical bytes. The lock file is operational metadata, not a second canonical profile. No schema migration guessed. On missing/invalid/disabled profile continue ordinary intake with a diagnostic and zero applied preferences, without weakening any required gate.

## Tools and integration

.systems/scripts/style-profile inspect|project are read-only. prepare previews a declared request and requires expected revision; apply writes only after the coordinator has verified actual scoped approval and source privacy. --request JSON fields: action, actor, source, approval, key, value (null key/value for init/enable/disable). --workspace absolute path; --path canonical relative path; --scope exact owner identity; --expected-revision 0 for init, current revision otherwise. The tool performs data validation, not authority authentication. Do not interpret its successful output as a phase PASS or permission grant.

Owner-visible usage: "owner-approved: enable this exact project style profile; record my explicit style corrections and marked generic observations here" establishes a scoped standing policy only when actual target/action/evidence are resolved. "Do not use/store my style" disables the approved profile; "that was only this task" must not become a durable general preference. A request containing private client context is not eligible training material. Further product-schema changes require the normal approved development/QA route.
